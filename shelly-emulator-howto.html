🔌 Bau dir dein eigenes virtuelles Shelly

Schritt-für-Schritt: ein Linux-Container, Raspberry Pi oder VM verwandelt sich in ein virtuelles Shelly Pro 3EM Energiemessgerät, das beliebige Datenpunkte (PV-Überschuss, Wetterdaten, Verbrauch eines Geräts, …) als „echtes" Shelly im Netz anbietet. Andere Shellys, die Shelly Smart Control App und Home Assistant sehen es ganz normal.

⚠ Was das ist — und was nicht

Das hier ist kein Hack der echten Shellys, sondern eine Reimplementierung der öffentlich dokumentierten Shelly-Gen2-RPC-API in Node.js. Andere Geräte / Apps fragen via HTTP nach Werten, du lieferst sie. Funktioniert komplett lokal, kein Cloud-Account nötig, kein Reverse-Engineering involviert.

📋 Was du brauchst

  • ✅ Linux-Host: Raspberry Pi 3/4/5, alter Mini-PC, LXC-Container, VM, NAS-Docker — egal, Hauptsache Linux mit Internet
  • ✅ Node.js ≥ 20 (kommt in der Anleitung mit)
  • ✅ Netzwerk im gleichen VLAN/Subnetz wie die Shellys oder Konsumenten (mDNS braucht Layer-2-Connectivity)
  • ✅ Eine Datenquelle die als JSON erreichbar ist (Wallbox-API, Solar-Inverter, eigene Excel-Tabelle als Static-File, …)
  • 🟡 Optional: 5-10 Minuten Geduld

🧩 Wie es funktioniert

   ┌────────────────────┐
   │  deine Datenquelle │  z.B. Solar-API, Wallbox, Sensor
   │  (liefert JSON)    │
   └─────────┬──────────┘
             │ HTTP-Poll (alle 10s)
             ▼
   ┌──────────────────────┐
   │  emulator (Node.js)  │  ← läuft als systemd-Service
   │  - /shelly           │
   │  - /rpc/Shelly.*     │  ← Shelly Gen2 RPC API
   │  - /rpc/EM.GetStatus │
   │  - mDNS announce     │
   └──────────┬───────────┘
              │ /rpc/... (via HTTP)
   ┌──────────┼──────────────────┐
   ▼          ▼                  ▼
 Shelly      Shelly         Home Assistant /
 Smart       Pro/Plus       Node-RED / ioBroker
 Control     mit Script     / eigene Tools

Das Gerät meldet sich via mDNS als _shelly._tcp.local im Netz. Andere Shellys und die Smart Control App finden es automatisch (Voraussetzung: gleiches Layer-2-Netz, also kein Router/VLAN dazwischen).

1️⃣ Source-Code holen

Wir nutzen die Implementierung aus dem Rosenweg-Repo (MIT-Lizenz, frei verwendbar). Komplett in JavaScript / Node.js, ein einziges File mit ~250 Zeilen plus eine Dependency.

Auf deinem Server einloggen und: 
mkdir -p /opt/shelly-emulator
cd /opt/shelly-emulator

# Source-Code von GitHub
curl -fsSL https://raw.githubusercontent.com/Rosenweg/Website/main/shelly-emulator/src/index.js -o index.js
curl -fsSL https://raw.githubusercontent.com/Rosenweg/Website/main/shelly-emulator/package.json -o package.json

# Node.js installieren (falls noch nicht da)
curl -fsSL https://deb.nodesource.com/setup_22.x | bash -
apt-get install -y nodejs

# Dependencies (nur bonjour-service für mDNS)
npm install --omit=dev

2️⃣ Datenquelle (BACKEND_URL) anpassen

🚀 Rosenweg Solar-Daten (PV-Anlage STWEG3): ready-to-use

Wenn du die Rosenweg-Solar-Werte nutzen willst, kannst du eine dieser Backend-URLs direkt in dein systemd-File schreiben — kein eigenes Backend bauen, kein Mapping nötig.

⚡ PV-Überschuss

https://www.rosenweg4303.ch/api/energy/shelly?variant=surplus

A = ohne Boiler · B = mit Boiler · C = Heizstab-Last

☀ Produktion + Verbrauch

https://www.rosenweg4303.ch/api/energy/shelly?variant=production

A = Solar-Produktion · B = Haus-Verbrauch · C = Netz-Bezug

🔌 Netz-Flussrichtung

https://www.rosenweg4303.ch/api/energy/shelly?variant=grid

A = Einspeisung · B = Bezug · C = Netto-Bilanz

Für andere Datenquellen (eigene Solaranlage, Wallbox, Inverter, Sensor): Der Emulator erwartet einen JSON-Endpoint der diese Felder liefert (alle in Watt):

{
  "phase_a_label": "Mein Wert 1",
  "phase_a_w": 1500,
  "phase_b_label": "Mein Wert 2",
  "phase_b_w": 3200,
  "phase_c_label": "Mein Wert 3",
  "phase_c_w": 700
}

Die _label-Felder sind optional und werden in der HTML-Statusseite des Emulators angezeigt. Wenn du sie weglässt, heißt es einfach „Phase A“ / „Phase B“ / „Phase C“.

Beispiel-Quellen die sich gut eignen:

  • Solar-Inverter (Fronius, Huawei, SMA, Solaredge) → kleines Mapping-Script in Python/Node davor
  • Wallbox-APIs (Easee, go-e, ABL Wallbox)
  • Home-Assistant mit REST-Sensor → /api/states/sensor.foo
  • Eigene MQTT-zu-HTTP Bridge
  • Static-File auf Webserver wenn Werte konstant sind

Du sagst dem Emulator wo seine Quelle ist via Environment-Variable BACKEND_URL.

3️⃣ systemd-Service einrichten

Damit der Emulator automatisch beim Boot startet und nach Crash neu lädt:

Datei /etc/systemd/system/shelly-emulator.service: 
[Unit]
Description=Virtual Shelly Pro 3EM Emulator
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/shelly-emulator

# === HIER ANPASSEN ===
Environment=PORT=80
Environment=BACKEND_URL=https://example.com/api/dein-endpoint
Environment=POLL_MS=10000
Environment=SHELLY_HOSTNAME=shellyvirtual1

ExecStart=/usr/bin/node /opt/shelly-emulator/index.js
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target

Aktivieren:

systemctl daemon-reload
systemctl enable --now shelly-emulator
systemctl status shelly-emulator    # check ob er läuft

4️⃣ Verifizieren

Vom Server selbst oder einem anderen Gerät im selben Netz:

# Browser oder curl auf http://<server-ip>/
curl http://192.168.1.50/rpc/Shelly.GetDeviceInfo
# Erwartete Antwort:
# {"name":"Rosenweg 9 PV-Ueberschuss (virtual)","model":"SPEM-003CEBEU",
#  "gen":2,"fw_id":"20251015-1.4.4","ver":"1.4.4","app":"Pro3EM",...}

curl http://192.168.1.50/rpc/EM.GetStatus?id=0
# {"a_act_power": 1500, "b_act_power": 3200, "c_act_power": 700, ...}

Wenn das funktioniert: Shelly Smart Control App öffnen → Gerät hinzufügen → Im Netzwerk suchen. Das virtuelle Gerät sollte erscheinen. Wenn nicht: manuell mit IP-Adresse hinzufügen.

5️⃣ Was du jetzt machen kannst

  • In der Shelly Smart Control App Scenes anlegen: „wenn Phase A Power > 1500 W für 5 min → Wallbox ein"
  • In Home Assistant die Shelly-Integration aktivieren — das virtuelle Gerät wird automatisch erkannt und liefert Sensor-Entitäten
  • In Node-RED einen Shelly-Node verwenden um auf Werte zu reagieren
  • In ioBroker als Shelly-Adapter hinzufügen für Visualisierung in VIS
  • Andere Shelly Plus/Pro-Geräte können via mJS-Script die Werte des virtuellen Geräts lesen (z.B. ein Shelly Plus 1PM steuert den Boiler basierend auf Überschuss)

🚀 Eigene Datenpunkte einbauen

Im index.js ist die Phase-Belegung im rpcEmGetStatus() definiert. Du kannst:

  • Phase A/B/C umbiegen auf andere Werte aus deinem JSON
  • Voltage / Frequency / PF anpassen (default: 230V / 50Hz / 1.0)
  • Mehrere virtuelle EM-Devices auf einem Server starten (verschiedene Ports + Hostnames)
  • Andere Shelly-Profile emulieren: SPSW-201X für Switch, SHEM-3 für 3-Phasen-EM Gen1

Vorlagen für andere Shelly-Modelle findest du in der offiziellen Shelly-API-Dokumentation.

🛡 Sicherheits-Hinweise

  • Der Emulator hat keine Authentifizierung — jeder im Netz kann die Werte lesen. Bei sensiblen Daten: vor das Gerät einen Reverse-Proxy mit Auth setzen, oder im strikten IoT-VLAN ohne Internet halten.
  • Niemals direkt ins Internet stellen. Wenn Remote-Zugriff nötig: VPN nutzen.
  • Die BACKEND_URL kann Secrets enthalten — Service-Datei nur mit chmod 600 lesbar machen.
  • Wenn du Cloud-Anbindung an Shelly Cloud willst: das geht nur wenn du die echte Shelly-Cloud-Authentifizierung implementierst (komplex). Standalone funktioniert problemlos.
